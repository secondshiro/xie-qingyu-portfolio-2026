# Edgecase Planner 连续稿

一次批量下载让我连续碰到三个问题。表头全选只覆盖当前页，文件打包时没有反馈，取消保存后系统却把任务记成已下载。它们分别涉及选择范围、等待状态和失败恢复，也成了我后来整理设计检查方法的起点。

我先把这些经验写成给 AI 使用的 Skill。设计前的 Plan 模式帮助我把范围、状态和恢复带进方案，设计后的 Review 模式用同一组问题检查真实表现。AI 看见分页和复选框时只能提出候选问题，业务答复和实际操作证据才决定它是不是缺陷。

设计师先提供界面、操作路径和已知条件。AI 围绕选择范围、状态连续性、异步反馈与恢复提问，设计师补充事实并确认取舍。输出保留问题、依据、结论和待办。证据不足时停在提问，不把猜测写成风险。

飞行计划设计稿提供了一次真实评审。航线弹窗允许勾选多条，确认区域却只显示一条。AI 追问一个计划能否同时使用多条航线。业务答复确认一计划一航线，我据此留下互斥单选的修正方向。原设计尚未修改，也没有线上修复记录。

后续一次材料提交评审暴露了提问方式的缺口。文件上传完成后，内容预审可能才开始。Skill 之前把两段等待合成一个问题，容易拿上传结果判断预审。我随后要求它先分清独立操作，再分别检查每一步的成功、失败和等待状态。

Arco 分步表单又带来一条新规则。页面提示链接必须以指定协议开头，实际输入普通文本仍能进入下一步。第一次运行 Skill 时，这个场景没有命中规则。我补入输入限制与纠错检查，再用原页面回查，形成一项有操作证据的格式校验问题记录。

当前交付包括 Plan、Review、检查规则、评审记录和未完成项。飞行单选仍待实施，Arco 页面也没有由我修改。这个工具只能帮设计师把问题问到有依据的位置，业务判断和修改决定仍由人完成。
