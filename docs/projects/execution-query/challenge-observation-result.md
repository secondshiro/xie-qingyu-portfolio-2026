# 当前验证码与真实浏览器闭环结果

## 最新结论

**有条件通过可行性闸门。**

2026-09-09 后续专用持久 Chrome 检查补充：不复制用户日常配置的空白专用 profile 首次能正常打开主页，三个验证码相关公开资源均为 HTTP 200，两个页面运行时对象已就绪。但填入非敏感词“测试”并点击查询后，15 秒内验证码主体未创建；同 profile 随后又出现表单无法显示。因此专用 Playwright profile 路线未通过真实验收。

2026-09-09 在用户已有的正常 Chrome 会话中，使用非敏感测试词“测试”完成了以下真实闭环：

1. 查询页加载完整。
2. 随机验证码弹层成功创建。
3. 在一次点选失败后刷新题目，站点在同一会话中从文字点选切换为拼图滑块，随后再切回文字点选。
4. 第二个文字点选题通过。
5. 同一会话自动发起列表查询，返回一条明显为站点测试用途的结果。
6. 点击“查看”后在新标签页完整加载详情结构。

该结果证明“验证码 → 列表 → 详情”在真实 Chrome 会话中可以走通。但这仍不是“生产自动验证已完成”：文字点选使用了本次代理视觉判断和桌面坐标操作，尚未封装为新工具的稳定求解器；拼图滑块的首次拖动没有通过。

## 随机性观察

同一站点、同一非敏感测试词、同一 Chrome 会话中已确认至少两类：

| 类型 | 真实出现 | 本轮结果 |
| --- | --- | --- |
| `SLIDER` | 是 | 已触发；首次拖动后题目刷新，不记为成功 |
| `WORD_IMAGE_CLICK` | 是 | 一次识别失败，一次识别并点选成功 |

站点会在单次失败或刷新后切换验证类型。因此不能把新版设计为单一滑块脚本；必须先识别类型，再调用对应处理器，且每次失败都必须重新识别当前题型。

## 浏览器边界

新建 Playwright Chrome 会话和用户已有 Chrome 会话表现不同：

- 新建 Playwright 会话：首页 HTTP 200，但验证码主脚本返回 400，弹层无法创建。
- 直连读取同一主脚本：HTTP 200。
- 全新浏览器上下文直接访问脚本：HTTP 200。
- 先访问首页再读取脚本：HTTP 400。
- 在诊断上下文清除站点 Cookie 后直接读取脚本：恢复 HTTP 200。
- 用户已有 Chrome 会话：页面、验证码、列表和详情均能加载。

这表明生产架构不应继续使用每个任务新建的临时 Playwright 会话。下一阶段必须优先验证专用、可持久化的 Chrome 用户数据目录，或者与用户真实 Chrome 会话协作的载体。不读取或复制用户日常 Chrome 配置。

## 已证明与未证明

### 已证明

- 当前站点的验证码会随机切换类型。
- `WORD_IMAGE_CLICK` 在真实 Chrome 会话中可由视觉识别与坐标点选通过。
