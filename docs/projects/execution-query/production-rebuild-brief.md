# 生产重构简报

## 产品目标

建立一个面向单个律师或小范围本地使用的批量查询工具：用户提交主体列表后，系统在真实浏览器会话中完成查询，保存可追溯结果，比较历史变化并导出工作表。用户应能看见每个主体处于等待、验证、查询、解析、完成或失败中的哪一步。

## 2026-09-08 的当前网站事实

本轮对 https://zxgk.court.gov.cn/zhzxgk/ 首页和脚本做了只读检查，确认：

- 页面加载 tianaiCaptcha.js 与 tianaiCaptchaRestPage.js。
- 前端定义了 SLIDER、ROTATE、CONCAT、WORD_IMAGE_CLICK 等验证类型；未指定类型时可由服务端选择。
- 验证相关路径为 /gkw/zhcx/captcha/captcha 与 /gkw/zhcx/captcha/captcha/check。
- 验证成功后，前端保存 captchaId 与 pCode，再调用 /gkw/zhcx/searchZhcx 和 /gkw/zhcx/detailZhcx。
- 对验证接口直接发原始网络请求会得到网站的 JavaScript 检查页。

这说明旧版“更新接口地址并继续用请求库”的路径不成立。验证码、浏览器状态、会话令牌和查询请求必须作为同一个真实浏览器流程研究。

## 风险边界

首阶段只回答一个问题：在正常访问频率和真实浏览器环境中，能否可靠完成网站提供的验证与查询流程。

不以隐藏自动化特征、规避访问控制、绕过风控或提高抓取频率为目标。若正常流程无法稳定自动化，或者网站条款与授权边界不允许，应把结论记录为闸门未通过，而不是继续扩大对抗手段。

## 为什么采用 FastAPI

FastAPI 适合承载：

- 提交批量任务与读取任务状态；
- 查询历史、差异结果与导出文件；
- 对前端提供稳定的数据合同；
- 隔离浏览器工作进程和页面界面；
- 为异常、日志、重试和测试建立清晰边界。

它不负责解决验证码。验证码可行性来自浏览器流程、网站适配器和真实运行验证。

## 建议的系统边界

    本地界面
      → FastAPI 服务
        → 任务与状态机
          → 浏览器工作进程
            → 网站适配器
            → 验证适配器
        → SQLite / 文件存储
        → 历史比较
        → Excel 与证据导出

默认先做本地单用户版本，不引入 Redis、Celery 或云端多租户。浏览器建议先以 Playwright Chromium 验证，最终选择仍以可行性测试结果为准。

## 建议的任务状态

| 状态 | 含义 | 是否可当作“无结果” |
| --- | --- | --- |
| queued | 已入队，未开始 | 否 |
| opening_site | 正在建立真实浏览器会话 | 否 |
| verifying | 正在完成当前网站验证 | 否 |
| searching | 已验证，正在查询主体 | 否 |
| fetching_details | 正在读取详情或分页 | 否 |
| completed_with_records | 查询完成且有记录 | 否 |
| completed_no_records | 查询成功且确认无记录 | 是 |
| verification_failed | 验证未完成或次数耗尽 | 否 |
| site_changed | 页面、字段或流程与适配器不一致 | 否 |
| network_failed | 网络或服务异常 | 否 |
| cancelled | 用户终止 | 否 |

只有收到可验证的成功响应并确认结果为空时，才允许写入 completed_no_records。

## 第一闸门：验证码可行性验证

### 输入

- 当前网站真实页面。
- 一组不含敏感信息的测试主体或经用户授权的最小样本。
- 固定版本的浏览器环境和运行日志。

### 必须覆盖

- 网站随机返回的各类验证形式是否能被正确识别。
- 验证完成后，captchaId、pCode 与查询请求是否处于同一有效会话。
- 单个任务失败后是否会清理状态，不污染下一任务。
- 有结果、无结果、验证失败、网站变更能否被准确区分。
- 限定重试次数和查询间隔后，是否达到可接受的连续任务完成度。

### 产出

- 可重复运行的最小实验。
- 每次运行的时间、验证类型、状态转换、结果分类和失败原因。
- 对可行、不稳定或不可行的明确结论。
- 不含敏感信息的证据截图或录屏。

### 通过标准的确定方式

下一轮计划必须给出具体样本量、成功阈值、最长等待、重试上限和停止条件。阈值不能在没有基线测试时伪造；应先做小样本基线，再由用户确认生产可接受度。

## 第二闸门：生产可靠性

验证码闸门通过后，才实现完整生产版本。至少需要：

- 批量输入校验与去重；
- 可取消、可恢复或可重新运行的任务；
- 原始响应、标准化记录和展示数据分层；
- 历史快照与新增、存续、撤销比较；
- Excel 导出；
- 任务级日志和失败原因；
- 同一真实会话产生的证据截图；
- 页面结构变化探测；
- 单元测试、适配器夹具和浏览器端到端测试。

## 数据与证据原则

- 原始查询数据仅保存在生产工具的受控本地目录。
- 数据库中记录来源时间、任务 ID、主体、状态和解析版本。
- 截图必须来自实际查询会话，不用脚本重绘浏览器外壳，不把注入后的静态数据称作实时查询。
- 公开作品集仅接收另行生成的脱敏副本。
- 日志避免记录完整身份标识和不必要的页面内容。

## 失效与停止条件

出现以下情况时应停止批量运行并提示用户：

- 网站结构或验证流程发生未知变化；
- 连续验证失败达到上限；
- 网站返回访问限制或异常检查页；
- 解析关键字段缺失；
- 查询响应与当前任务的会话无法确认对应；
- 结果落盘失败。

停止意味着保护结果可信度，不代表工具把失败当成空结果。
