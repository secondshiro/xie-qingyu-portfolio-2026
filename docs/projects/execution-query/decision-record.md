# 决策记录

## 真正要解决的问题

律师需要反复在目标网站查询多个主体，并持续保存结果、比较历史变化、导出工作记录。旧流程的主要成本不是一次查询本身，而是不断刷新、处理验证、逐条进入详情、复制信息以及重复比对。

因此，新版的成功标准不是“能展示一次查询”，而是：

1. 在合理频率下连续处理一批真实任务；
2. 明确区分查询成功、无结果、验证失败、网站变更和网络故障；
3. 留下可复核的历史、变更与导出结果；
4. 让律师不必把时间消耗在重复验证和人工抄录上。

## 已确认的用户判断

| 变量 | 已确认决定 | 对方案的影响 |
| --- | --- | --- |
| 是否承担生产工具责任 | 承担 | 不能只做展示原型，必须定义错误状态、证据与数据可靠性 |
| 是否接受人工验证码作为日常流程 | 接受人工接管 | 验证保留为网站要求的真人节点，工具聚焦批量、接续、历史与导出 |
| 能否展示真实结果 | 能，公开时模糊或打码 | 可建立真实证据链，但必须把原始证据与公开副本分开 |
| 是否承诺长期维护 | 不作为作品集承诺；网站变化时再改 | 案例要标注阶段和验证日期，工具仍需能检测失效 |
| 生产价值与作品集价值是否冲突 | 对用户而言一致 | 页面应讲生产问题和工程判断，不另造一套展示故事 |
| 是否采用 FastAPI | 在有帮助时采用 | 用于服务边界和任务管理，不把框架包装成验证码解决方案 |

## 双向钢人后的判断

### 支持做成生产工具

- 它来自清晰而持续的实际痛点，解决的是高频重复劳动。
- 旧版已经形成从单次查询到批处理、历史比对、导出和证据截图的演进链。
- 作品集可以呈现产品判断、失败修正、风险边界和真实工作流，而不仅是一张视觉稿。
- 生产工具和作品集案例使用同一套事实，能显著提高可信度。

### 反对直接进入全面重写

- 当前网站的验证方式和风控已经改变，验证码是否能在正常、合规的浏览器流程中可靠完成尚未证明。
- 一旦把验证失败误判为“无结果”，法律工作场景中的风险高于节省的时间。
- 旧版中请求会话、页面注入、模拟浏览器外壳和截图生成混在一起，继续局部修补会放大不可测试性。
- 若先做完整界面和后端，再发现验证码不可稳定处理，大部分开发投入会失去前提。

### 2026-09-10 最终裁决

本地图像识别试验的资源成本持续上升，且无法证明随机题型与行为校验足以稳定支持生产。产品方向据此调整：

1. 停止把自动验证码作为发布闸门；
2. 所有验证都交给用户在当前执行网页面完成；
3. 页面验证成功后，工具自动接续当前项，并在有效期内复用页面会话处理后续主体；
4. FastAPI 承担批量任务、SQLite 历史、失败语义和 Excel 导出；
5. 定时能力只做创建待办与提醒，不在后台绕过验证；
6. 作品集公开呈现这次边界重画，同时把真实浏览器终验保留为独立阶段状态。

### 2026-09-12 产品入口调整

浏览器扩展若要求用户先打开官网、理解侧栏并手动发起任务，会把产品退化成网页增强插件。当前结构改为：

1. FastAPI 本地控制台是唯一推荐入口，承接名单、进度、历史、变化比较和 Excel；
2. Chrome 扩展退到后台，作为连接本地任务与官网会话的浏览器桥梁；
3. 用户不必预先打开执行网，桥梁自动复用已有页面或在后台新建；
4. 只有网站提出安全验证时才把官网带到前台，验证完成后自动返回批量流程；
5. 产品价值用人工介入频率、批量接续和结果可信度判断，而不是用“官网是否曾经出现”判断。

### 2026-09-13 现场验收裁决

真实浏览器小样本闭环已经通过。一次人工文字点选验证后，两项合成任务连续完成。第一项取得列表与详情，第二项复用同一页面会话并确认无记录；三表 Excel 从同一任务导出并通过结构、公式错误和视觉检查。

这次结果关闭“真实浏览器终验待完成”的阶段状态，也确认了当前产品定位。人工验证保留为官网节点，工具负责名单、接续、详情、历史与导出。公开案例可以写“小样本闭环通过”，仍不能写成无人值守、已上线或长期稳定运行。

## 明确不做

- 不把旧版换皮后称为新版。
- 不以 OCR、识别率或“零人工”作为未经实测的营销口号。
- 不伪造浏览器界面、运行时间、查询结果或业务指标。
- 不承诺永久兼容第三方网站。
- 不隐藏失败，也不自动把失败写成空结果。
- 不开展规避风控、对抗访问限制或高频抓取。
- 不保存验证码图片、题目、坐标或页面验证票据。
